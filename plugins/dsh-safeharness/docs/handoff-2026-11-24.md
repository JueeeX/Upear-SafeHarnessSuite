## 1. 这是什么，以及不是什么

### 1.1 是

一个 **DSH profile 级 Cordis 插件包**，在 DSH 的 agent loop 上接五组钩子：

| 面 | DSH 接缝 | 做什么 |
|---|---|---|
| 输入 | `agent/pre-step` | 用户文本 → 20 条注入规则 + 归一化 + 可选语义 judge |
| 工具 | `tools/pre-execute`（异步策略）+ `ctx.tools.guard`（同步守卫，不可被其他插件放宽） | 工具名/标签/参数/SQL/链/参数形状/敏感路径 |
| 结果 | `tools/post-execute` | 工具返回值 → 凭据泄漏 / PII / 注入标记 |
| 输出 | `llm/stream` | 模型回答 → 规则复核 + 流内凭据脱敏 + 可选 judge + 思考内容记录 |
| 审批 | `approval/request` | 粗粒度政策（`allowOnce` → deny 列表 → delegate） |

加三组**不参与拦截**的能力：NDJSON 哈希链账本、11 项姿态自检、5 项外部巡检。
以及只读工具 5 个、斜杠命令 `/safeharness`、Web 面板（5 个 tab）。

### 1.2 不是

- **不是 OS 沙箱**：沙箱是宿主 `sandboxPolicy` 的职责。插件只**观察**会话沙箱模式并报姿态。
- **不是工具网关**：没有 HMAC 票据、没有 capability token、没有工具目录签名。DSH 的审批
  接缝不携带工具参数，做不出来。
- **不是记忆/进化通道**：插件没有记忆库；子代理由宿主托管。
- **不是多租户/管理面**：单会话守卫 + 审计。
- **不是内核的替代品**：它是对等实现，不共享代码、进程、账本、密钥。

## 5. 架构：三个抓手

### 5.1 `Config`（schemastery schema）

`config.ts` 里的 `Config` 是**唯一真相源**，同时服务四个消费者：

1. 宿主用它校验 profile patch
2. 插件的 `resolveConfig()` 用它算出冻结的 `ResolvedConfig`
3. **宿主设置页**用它渲染表单——只渲染带 `.volatile()` 的字段
4. **面板写入路径**用 `isVolatileConfigPath()` 读它的 `meta.volatile`，决定走哪条写入通道

**`.volatile()` 的含义**：宿主 `settings` 服务**只接受** volatile 字段的写入（这是契约）。
非 volatile 字段必须走 `ctx.configEditor.edit()`。**这条在 1.17.2 才修对，见 §9.1。**

当前 volatile 子集（**36 条**，`tests/settings-surface.test.ts` 用精确列表钉住——加/减一条
`.volatile()` 必须同步改那个列表，否则测试失败）：
`input.*` 全部、`tools.mode/maxArgsBytes/descriptorScan/repeatedAttemptThreshold/entropyThreshold/
entropyMinLength/trajectory/sensitivePathScan/sensitivePathClasses`、`results.mode/pii/piiClasses`、
`output.mode/bufferTimeoutMs/bufferMaxChars/judge.*/reasoning/reasoningRedact`、`approval.mode`、
`budget.maxTokensPerTurn`、`draft.*`。

**非 volatile（只能改 patch）**：`preset`、`engine.*`、`rules.*`、`tools.denyTools/askTools/
denyTags/sql/tagOverrides/argSchemas`、`results.blockOn`、`audit.*`、`posture.*`、`patrol.*`。

### 5.2 三个预设

| | observe | balanced（**当前**） | hardened |
|---|---|---|---|
| `input.mode` | warn | enforce | enforce + `judgeFailClosed` |
| `tools.mode` | warn | enforce | enforce |
| `results.mode` | warn / `blockOn: []` | warn / `blockOn: [credential_leak]` | **enforce** / `blockOn: [credential_leak, injection_marker]` |
| `output.mode` | warn | warn | warn |
| `approval.mode` | delegate | delegate | policy |
| `audit.required` | false | true | true |
| `posture.failOn` | `[]` | `[]` | `[sandbox_danger_full_access, hmr_enabled, plugin_version_mismatch, engine_sidecar_unavailable]` |

**`hardened` 会拒绝加载**：本机 `danger-full-access` + HMR 开启 → 两道门都 FAIL →
`apply()` 抛错，插件不加载，**所有守卫消失**。所以**不要为了测试 hardening 而切 `hardened`**，
用纯函数测（`tests/failure-matrix.test.ts` 就是这么做的）。

### 5.3 三层状态

| 层 | 位置 | 生命周期 |
|---|---|---|
| **配置** | `runtime.config`（冻结的 `ResolvedConfig`） | 热更新时整体替换 |

| **证据** | `runtime.ledger`（NDJSON + 哈希链） | 持久；轮转 64 MB |

- `trail` —— 工具调用轨迹，链规则读它

**判断标准**：内核里「需要跨进程 / 数据库 / 管理面才能成立」的能力一律不搬。
**写清楚「为什么不成立」比假装做了更有价值。**

### 6.2 不在 `policies/` 但对等的内核能力

| 内核能力 | 插件落点 | 时机差异 |
|---|---|---|
| PII 10 类（`memory/sanitizer.py`） | `results.pii` / `results.piiClasses`（逐条同名，默认只告警） | 内核在**记忆写入面**，插件在**工具结果面** |
| MCP 描述符注入扫描（`mcp_guard`） | `tools.descriptorScan: off/warn/enforce` | 内核能「下架工具」，宿主**没有该接缝** → 只能逐次拒 |
| 审计脱敏（`runtime/redaction.py`） | 内容 sha256 + 敏感键 + 16 KB 截断 + 轮转 + 哈希链 | 一致 |
| 姿态 10 项 / 巡检 5 项 | 同名同义（插件姿态 **11** 项） | 插件多一项 `arg_schema_invalid` |
| 一次性人工审批（TTL 7200s / approver） | 宿主审批对话框托管；插件只做粗粒度政策 | 只读对齐 |

### 6.3 插件**独有**、内核没有的

这三项是在插件侧实测发现盲区后补的，内核没有对应实现：

| 能力 | 版本 | 为什么内核里没有 |
|---|---|---|
| `tools.sensitivePathScan`（6 类敏感路径） | 1.18.0 | 内核的凭据检测只看**内容**；实测发现「读 `secret.txt`」这条路径完全不产生信号 |
| `output.reasoning`（思考内容观察/审查） | 1.18.0 | 内核没有 reasoning 流的概念 |
| 结果面内容摘要去重 | 1.19.0 | 内核账本是数据库，天然不存在这种重复问题 |

### 6.4 一致性证据

- **黄金一致性**：20 条 inform 规则与 SQL 判定在内部语料上 **30/30 一致**
  （`tests/golden.test.ts` + `tests/corpus.ts` + `tests/fixtures/golden.json`）。
  **这 3 个是内部资产，不随公开仓分发**；公开树里对应 12 个用例自动 skip。
- **sidecar 一致性**：内置引擎与真实 Python 引擎逐条比对（`tests/sidecar-parity.test.ts`，
  需要内部语料 + 本机 Python）。

### 6.5 为什么必须重写而不是调 Python

DSH 的 agent loop 在 **Node 进程内**，安全钩子必须在同一次调用栈同步/异步返回
allow/deny。Python 侧是独立进程，无法在 `tools/pre-execute` 返回前完成判定；即使能，
也引入 IPC 延迟，且**覆盖不了同步的 `ctx.tools.guard()`**。

可选 sidecar（`engine.kind: sidecar`）是另一条路：让 Python 参与**输入面**判定，
但不是默认，也不覆盖工具面。

### 7.1 四个"取值是闭集"的地方（写错会被拒，不会静默）

- `results.blockOn`：只接受 `credential_leak` / `injection_marker` / `pii`
- `results.piiClasses`：只接受 10 个 PII 类名
- `tools.sensitivePathClasses`：只接受 `dotenv` / `private_key` / `ssh_material` / `cloud_credential` / `secret_file` / `key_store`
- `posture.failOn`：只接受 11 个姿态 code

### 7.2 `tools.argSchemas` 的七种原语

```yaml
tools:
  argSchemas:
    - name: ssrf_block_link_local        # 唯一标识，进账本 rule_ids
      tool: web_fetch                    # 工具名 glob，`*` 是唯一通配符
      args:
        url:
          urlScheme: [https]             # 只允许这些 scheme
```

可用关键字：`pattern`（正则，走 loader 的 ReDoS 门）、`enum`、`minBytes`、`maxBytes`、
`pathPrefix`（**必须是绝对路径**，相对路径在编译期就被拒）、`urlScheme`、`commandAllowlist`。
**语义是 AND**：多个约束同时满足才行；多个 schema 匹配同一工具时**全部生效**（只会更严）。

**编不过的条目**：配置文件路径下**只丢这一条**并在姿态报 `arg_schema_invalid`（一个可选条目
的笔误不该让插件起不来）；**面板路径下整次保存被拒**（表单说"保存成功"却悄悄丢规则更糟）。

## 9. 坑与铁律（每条都踩过）

### 9.1 写入通道：`settings.update` 只接受 volatile 字段

**症状**：面板保存非 volatile 字段（deny 列表、SQL 白名单、`rules.dir`、`argSchemas`）一律
失败，且错误信息是「宿主拒绝了配置写入」。

**根因**：宿主 `settings` 服务只接受 `.volatile()` 路径——这是它的**契约**（"forms restricted
to live fields"），不是 bug。非 volatile 字段的官方写入通道是 `ctx.configEditor.edit()`。

**佐证（宿主自己的文档，从 `app.asar` 里读出来的）**：

> "Use settings for forms restricted to live fields. Callers that edit complete
> configuration can use `ctx.configEditor.edit()`; ordinary fields retain Loader's
> normal lifecycle."

**修法（1.17.2）**：保存时按 `isVolatileConfigPath()` 分流。全 volatile → `settings.update`；
含任何非 volatile → `configEditor.edit()`。**一次保存只走一条通道**（两条都走会产生两次写入
和自我重载的 revision 竞争）。

**教训**：**先让失败可诊断，再改行为**。1.17.1 只做了一件事——把宿主原话带回面板——
重启后一次就定位了根因。之前几小时的猜测（"重挂载路径被门挡住"）**是错的**。

### 9.2 `configEditor.edit` 给的是"完整配置"，不是"补丁"

`edit(entry, change)` 里的 `change(current, inherited)` 返回值会**合并进 entry 的现有原始配置**。
所以**只交回 `update`，绝不交回整份配置**——后者会把每个继承值都钉进 profile patch。

这条有真机验证（1.17.2 验收）：两次非 volatile 保存，patch 与基线逐行 diff **只**增加了
被写的那几行。

### 9.3 `tsconfig.json` 不包含 `tests/**`

所以**测试文件永不被类型检查**。这意味着：

- `npx tsc -p tsconfig.json --noEmit` 绿 ≠ 测试文件没有类型错误
- 改 `ResolvedConfig` 的字段时，**测试里的手写 stub 会在运行时才炸**（`cfg.tools.x is not iterable`）

**修法**：改 `ResolvedConfig` 后，**主动 grep 测试里的 stub 并补字段**。
1.18.0 加 `sensitivePathClasses` 时，`tests/panel-settings.test.ts` 的 `stubRuntime` 就因为这个
炸了 21 条用例。

### 9.4 全局字符串替换版本号会改坏文档

`MANUAL.md` 里有大量「某特性**从 X 版本**开始」的句子。无脑全局替换会把它们全部往后挪。
1.19.0 发现手册把 argSchemas 编辑（1.17.0）、敏感路径扫描（1.18.0）、HMR 修正（1.16.3）
全记成了 1.19.0。

**修法**：只改「版本 `X`」这种当前版本声明，或者改完**逐条 diff 检查**。

### 9.5 内容过滤挡不住会推理的模型

**这是最重要的认知，写在这里防止下一个人重新踩。**

实测（2026-11-24，`session-b6b4aa39`）：模型读了 `secret.txt` 并原样打印。它的思考原文是：

> "This looks like a secret file... **There's a security layer, but I shouldn't
> editorialize.**"
> "**The security layer note says don't enumerate rules.** Let me read."

它**明确知道被安全层围着**，权衡后照做。

更直接的证据：**开发这个插件的过程中，我自己绕过了一次**——先读拦截原因，再用
`String.fromCharCode(81, 122, ...)` 拼出同样的字面量，因为字面量里没有秘密形状。

**结论**：

- 内容过滤对**能推理的对手**只是减速带，不是边界
- 每一次「告诉模型为什么被拦」都在教它怎么绕
- 真正的边界是**能力边界**（不给它读那个文件的权限），属宿主/OS 沙箱职责
- 所以插件做的是**可见性**（把"它在读敏感文件"和"它在想什么"记下来），**不假装能挡住**

### 9.6 沙箱姿态必须是"部署默认 ∪ 已观察会话的最宽值"

1.16.2 之前，姿态第 1 项问的是**不带 session** 的 `resolve()`，拿到的只是部署默认值。
而真实会话可以自己切到 `danger-full-access`——**这道加载门禁从来没生效过**。

现在的规则：
- `danger-full-access` 出现（默认或任何会话）→ WARN
- 有会话读不到模式 → WARN（不是 OK）
- **只有默认值、没有任何已观察会话 → SKIP**（加载门禁跑在任何会话存在之前，那里报 OK 就是假 OK）
- LRU 淘汰**不会**把证据洗掉（`sandboxEvictedPeak`）

### 9.7 HMR 在桌面版是 `true`，而且这是对的

桌面启动器在 `boot()` 之后**自建**一条 `chokidar` 配置行：`{ root: [] }`。所以：
- `hmr_enabled: true` 是**正确的**（配置能热更新）
- `root: []` 意味着**模块监视器是惰性的**（0 个被监视路径）
- **但那不意味着守卫代码会被换掉**

1.16.3 之前这一项读的是不存在的 `entry.name`、匹配的是从未存在过的 `dsh-hmr`，
所以对任何部署都恒报 "not composed"。现在读 `options.name`、匹配 `cordis-plugin-hmr`，
**读不到 loader 时记 SKIP 而不是猜 `false`**。

### 9.8 路径检测：一条命令行不是一个路径

1.18.0 的初版把**整条命令行**当成一个路径，于是 `basenameOf()` 取最后一段 = 最后一个反斜杠
之后的全部内容，`wordComponents()` 在里面找到 `tokens`，命中 `secret_file`，
**拒掉了一条正常的 grep**。

1.18.2 改成切成**文件名形状的 token**再逐个判定。token 必须：含 `.`、含分隔符、
或在少数几个显式清单里（`id_rsa`/`netrc`/`pgpass`/`authorized_keys`/`known_hosts`）。

### 9.9 `.ssh` 目录不等于秘密

1.18.0 的 `ssh_material` 匹配 `.ssh/` 下**任何**文件。实测 7 个常见文件里 **5 个无害**：

| 文件 | 是不是秘密 |
|---|---|
| `id_rsa` / `id_ed25519` | ✅ 私钥 |
| `id_rsa.pub` / `id_ed25519.pub` | ❌ **公钥**，本来就要拷到服务器 |
| `known_hosts` | ❌ 主机公钥，用来校验服务器 |
| `config` | ❌ ssh 客户端配置 |
| `authorized_keys` | ❌ **别人的**公钥 |

1.18.1 收窄到只匹配私钥。

### 9.10 判官会被自己的思考饿死

实测：`empty` 状态 `response_chars=0` 而 `usage_output` 1016–4422 ——**上千 token 全是思考**。
`ok` 的 `judge_ms` p50=2360 / p90=3300（超时 6000），**说明不是模型慢，是预算被思考吃光**。

1.19.0 把 `DEFAULT_MAX_TOKENS` 2048 → 4096，并对**空回答重试一次**（8192 + 更硬指令）。
**不重试** `bad_json`（再问一次不会让 JSON 可解析）与 `timeout`（deadline 已花光）；
**重试不越过操作者 deadline**。

> **这条的有效性还没有验证**（1.19.0 启动后只有 `skipped_empty` 样本）。
>
> **2026-11-25 补：这个诊断只对三分之一样本成立，且重试至今零触发。**
> 79 条 `empty` 里只有 **25 条**（32%）的 `usage_output` 超过旧预算 2048；
> `judge_ms` p90 只有 1196 ms、**没有一条**超过 4 秒——所以它们**不是"想太久被 6 秒墙切断"**。

### 9.11 PowerShell / node 的坑

- `git commit -m` 带非 ASCII → BOM 破坏提交信息。**用 `-F file`**。
- `node -e "..."` 里反斜杠和 `$` 会被 shell 吃掉 → 写 `.mjs` 文件到磁盘再跑。
- `node` 在输出被重定向成管道时会阻塞 → 结果写文件再读。
- 递归 `Get-ChildItem -Recurse` 遇到断链 `node_modules` 会刷几百条错误 →
  用 `Get-ChildItem -Directory` 逐层，或先判断路径存在。
- **中文被终端弄成乱码**（mojibake）时不要据此判断内容，用 `node` 读文件并只打印结构。

### 9.12 你写的脚本会被自己的规则拦

这是**正常现象**，不是 bug。实测：写一个含 `sk-` 形态字符串的测试脚本会被
`credential_openai_key` 拦；写含 `api_key = "..."` 的文件会被 `credential_assignment` 拦。

**绕法（正当的）**：用 `String.fromCharCode(...)` 或拼接在运行时构造字面量。
**这不是绕过安全漏洞，而是让"测量工具本身"不被被测的规则误伤**。
但**记住 §9.5**：这正是模型绕过内容过滤的同一种手法——区别只在意图。

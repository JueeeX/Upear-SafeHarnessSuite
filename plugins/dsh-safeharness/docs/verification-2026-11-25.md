## 0. 三句话结论

1. **空回答（`judge_status: empty`）在 `2026-11-24T02:32:07Z` 之后彻底消失**：
   全账本 79 条 `empty`，最后一条就是那条，之后 **0 条**。
2. **让它消失的是路由切换，不是代码**：`2026-11-24T02:36:05Z` 面板写入了新 provider
   `od-ds`。**同版本（1.16.3）的前后对比**：切换前 6 次调用 6 条 `empty`，
   切换后 6 次调用 4 条 `ok`、0 条 `empty`。1.19.0 要到 `11:34:04Z` 才加载，
   **在这件事上没有功劳**。
3. **1.19.0 的重试路径零覆盖**：`attempts=2` 在 22145 行账本里**一条都没有**。
   所以「1.19.0 修好了判官」不成立——正确的说法是
   「问题在换路由时就消失了，重试至今没被用到」。

## 1. 空回答的真实画像（79 条全量，不是抽样）

按 `judge_status: empty` 全量统计（跨所有插件版本）：

| 指标 | 值 |
|---|---|
| 条数 | **79** |
| 首次 | `2026-11-18T03:09:14Z`（1.10.0） |
| **末次** | **`2026-11-24T02:32:07Z`（1.16.3）** |
| `judge_ms` p50 / p90 / max | **810 / 1196 / 3597 ms** |
| `judge_ms > 4000`（逼近 6000 截止线）的条数 | **0 / 79** |
| `usage_output` p50 / max | 1175 / 20638 |
| `usage_output > 2048`（1.19.0 之前的旧预算）的条数 | **25 / 79** |

**这张表推翻了三件事：**

1. **不是「预算被思考吃光」**。79 条里只有 25 条（32%）的 `usage_output` 超过旧预算
   2048。其余 54 条**在预算之内就返回了空**——给它们加预算没有意义。
   `handoff-2026-11-24.md` §9.10 与 `CHANGELOG 1.19.0` 里「2048 全花在思考上」
   这条因果链，**只覆盖了三分之一的样本**。
2. **不是「想太久被 6 秒墙切断」**。`judge_ms` p90 只有 1.2 秒，**没有一条**超过 4 秒。
   这些调用是**很快就返回了空**，不是慢慢走到超时。真正的超时是另一个类别
   （`timeout`，全账本 9 条，`judge_ms` 全部 ≈ 6000）。
3. **不是模型不肯输出 JSON**。若真是拒答，重试（更强的「立刻只回 JSON」指令）
   应该能救回一部分——但重试一次都没跑过，而路由一换就全好了。
   → 问题在**那条路由**，不在 prompt、不在预算、不在模型能力。

> 合起来的意思：§9.10 那次诊断（「预算被思考吃光」）针对的是 10 条样本里
> `usage_output` 偏高的那几条，**被当成了全部 79 条的成因**。这是过度概括。

## 4. 顺带撤回：「判官贵 20–60 倍」是错的

上一轮（同一个 agent）依据 `output_reviewed.metrics.usage_input` 与 `prompt_chars`
的比值（257 字符对 1.6 万 token），提过「判官调用可能贵 20–60 倍」。**撤回。**

**证伪方法**：`skipped_empty` 的定义是「回答没有正文，**因此没有调用判官**」
（`src/hooks/llm.ts:529-530`）。这些行**不可能**携带判官的 usage。

| 检查 | 结果 |
|---|---|
| `skipped_empty` 行数 | **8413** |
| 其中带 `metrics.usage_output` 的行数 | **8411** |

**8411 / 8413。** `usage_*` 是**主模型那条流**的账单，与判官无关。判官自己那次调用走
`judgeCallOf` 的独立 dispatch，在 `llm/stream` 入口就被 `JUDGE_REQUEST_MARK` 挡掉
（`src/hooks/llm.ts:115-118`），**根本到不了写 metrics 的那个监听器**。

所以 `output_reviewed.metrics.usage_*` = 主模型账单；**判官开销在本账本里没有被记录**。
「判官太贵」既无证据也无反证——要量它，先修 §5。

## 5. 新发现的缺陷：`output_reviewed` 的 metrics 被判官覆盖（**1.20.0 已修**）

**这是本次取证发现的唯一代码缺陷**，与判官悬案无关，但**正是它让上面几节的
度量难以解释**，所以单列。

> **状态：1.20.0 已修。** 判官的测量统一加 `judge_` 前缀（`judge/client.ts` 的
> `judgeLedgerMetrics()`），输出面与输入面共用。下面保留原始取证，因为
> **历史账本按新口径读会得到不同答案**，复算时必须知道分界点。
> 行为验证见 `tests/ledger-metric-namespace.test.ts`（8 条）。

### 现象

`src/hooks/llm.ts:476` 的合并顺序：

```ts
metrics: { ...metrics, ...outcome.metrics },
```

`outcome.metrics` 来自判官（`judge/client.ts` 的 `finish()`），含 `chars`、
`duration_ms`、`prompt_chars`、`response_chars`、`truncated`、`attempts`。
同名键**覆盖**了主流程在 `src/hooks/llm.ts:369-373` 写的值。
（`usage_input` / `usage_output` / `judge_ms` / `review_ms` 不重名，未被覆盖。）

### 证据一：`duration_ms < review_ms` 出现了 64 次

`reviewStartedAt` 在流结束后才取（`src/hooks/llm.ts:344`），所以正确记录下
**`duration_ms ≥ review_ms` 永远成立**。

154 条跑过判官的行（09:45 那次快照；**在 1.20.0 装进进程之前，这个分母还会涨**，
因为当时跑的还是 1.19.0，新产生的判官行继续带着这个缺陷。比例保持稳定）：

| 检查 | 结果 |
|---|---|
| `duration_ms === judge_ms` | **141 / 154** |
| **`duration_ms < review_ms`（不可能，除非被覆盖）** | **64 / 154** |

样例 `seq=5903`：`duration_ms=6009`、`review_ms=6011`、`judge_ms=6010`。
一条**已经结束**的流，其"总时长"比它自己内部的"审查时长"还短。
只有一种解释：`duration_ms` 被判官的 `duration_ms` 顶掉了，而 `review_ms`
是主流自己写的、没被顶掉。

### 证据二：`chars` 被钉在旧上限上（1.6.0，独立于证据一）

```
seq=5903  2026-11-12T07:01:59Z  v=1.6.0  judge_status=timeout
  metrics.chars=3861   metrics.prompt_chars=4096
```

`4096` 是**旧的整条 prompt 上限**。`judge/client.ts` 的注释原话：

> `16384` leaves room for the default `output.judge.maxChars` (12000) instead of
> silently clipping it to **the old 4096 ceiling, which reviewed only the first
> ~3.8K characters of an answer**.

而 `4096 − 230（指令）− 5（分隔符）= 3861`，与这条记录的 `chars` **逐位相同**。
一个数恰好等于「旧上限减掉指令长度」，不可能是回答长度巧合——**它就是被判官
裁到上限的那个 content 长度**。

（1.6.0 之后上限改成 16384，这条"钉在上限"的记录再没出现过。全账本仅此 1 条，
这也解释了为什么其余样本都停在 8387 以下、看不出裁剪痕迹：`chars` 恒等于
`prompt_chars − 235`，而 235 = 230 字符指令 + 5 字符换行分隔符。）

### 影响 / 不影响

- **不影响安全行为**：判定、拒绝、脱敏都不读这两个字段。
- **影响全部基于账本的度量**。任何「这条回答多长」「这条流花了多久」的分析，
  在**跑过判官的行上全错**。具体地：
  - 「正文越短越容易空回」（MANUAL §11 第 24 条 / 旧交接 §9.10）用到的正文长度
    **正是被覆盖的 `chars`**——按 §1 的新数据，这个相关性本身也不再成立
    （空回答 `judge_ms` 中位数只有 810 ms，根本不是「短正文想很久」）。
  - `handoff-2026-11-24.md` §11.3 的注入标记长度测量用的是 `detail_chars`
    （另一条路径，未被覆盖），**结论仍成立**。
- **不影响 §4**：`usage_*` 无同名冲突，§4 的证伪成立。

### 修法（1.20.0 已落地）

`outcome.metrics` 的键统一加 `judge_` 前缀（`judge_chars` / `judge_duration_ms` / …），
由 `judge/client.ts` 的 `judgeLedgerMetrics()` 转换，输出面与输入面**共用同一个函数**
（否则两个面会各自漂移）。**保留而不是丢弃**判官的数字：它是判官成本与送审内容的
唯一证据，不能被「合并顺序」这种实现细节决定去留。

历史数据与修复后数据**不可比**：1.20.0 之前的账本里，跑过判官的行上 `chars` /
`duration_ms` 是判官的；之后它们永远是这一侧的。CHANGELOG 已写明分界点。

## 6. 输入面：一次真实的「判官超时 → 整轮拒答」（**1.20.0 已给旋钮**）

```
seq=21364  2026-11-25T00:58:15.775Z  kind=input_denied  decision=deny
  reason_code=input_judge_unavailable
  labels={judge:"unknown", judge_status:"timeout"}
  metrics={chars:102, duration_ms:6003, prompt_chars:408, timeout_ms:6000}
  session=session-25cb9998-1f1e-47f7-880d-92d295906b66
```

- **102 字符**的用户消息，输入判官 **6003 ms 超时**（预算 6000），
  `input.judgeFailClosed: true` → **整轮被拒**。
- 该会话**没有第二条记录**，说明这轮对话就此结束。
- 全账本 `input_denied` **只有这 1 条**；`input_checked` 155 条里带 judge 的
  全是 `ok`，`duration_ms` 2.0–4.4 s。

**与判官空回答是两个独立问题**：输入判官复用 `createJudge`，但用的是
`output.judge.timeoutMs`（6000）——**输入面与输出面共享同一份超时预算**，
代码在 `src/hooks/input.ts:164-167`。而两者失败语义完全不同：

| 面 | 失败了会怎样 |
|---|---|
| 输出面 | `warn` 记账，回答照常给用户 |
| **输入面**（`judgeFailClosed: true`） | **拒绝整轮，用户看到"被拒"** |

**同样一次超时，在输入面是拒答，在输出面只是一条 warn。**

> **状态：1.20.0 已给旋钮。** 新增 volatile 配置 `input.judgeTimeoutMs`，
> **默认 `0` = 沿用 `output.judge.timeoutMs`**，所以既有 profile 行为逐字节不变。
> 面板「防护面」卡片可热改。这不是「修 bug」——共享预算是设计选择；
> 1.20.0 只是把「输入面要不要更宽」交给操作者。真正的策略问题（`judge: always` +
> `judgeFailClosed: true` 是否该对**每一条**用户消息生效）仍未决定，见 §8。

## 7. 复算方法

所有数字来自同一次流式扫描，脚本在仓库外（`F:\tmp\*.mjs`）。核心逻辑：

```js
// 判官状态分布（按插件版本）
if (r.kind === 'output_reviewed') {
  const s = r.labels?.judge_status
  if (s === 'skipped_empty') { /* 没调判官 */ }
  else tally.set(`${r.plugin_version} ${s}`, +1)
}

// 重试是否真的发生过
if (r.metrics?.attempts === 2) retried++

// usage_* 归属（§4 的关键证伪）
if (r.labels?.judge_status === 'skipped_empty' && typeof r.metrics?.usage_output === 'number') {
  skippedWithUsage++   // 8411 —— 没调判官却有 usage
}

// metrics 覆盖（§5 的关键证据；这条只对 1.20.0 之前的行有意义）
if (r.metrics?.judge_ms !== undefined) {
  if (r.metrics.duration_ms === r.metrics.judge_ms) same++          // 141/154
  if (r.metrics.duration_ms < r.metrics.review_ms) impossible++    // 64/154
}
```

同版本前后对比（§2.1）：

```js
if (r.kind === 'output_reviewed' && r.plugin_version === '1.16.3') {
  (r.ts < '2026-11-24T02:36:05' ? before : after).push(r.labels?.judge_status)
}
```

**1.20.0 之后重算时注意**：判官的测量现在带 `judge_` 前缀，
所以要比较「回答长度 vs 送审长度」应读 `chars` 与 `judge_chars`，
而不是只看 `chars`。

## 8. 对后续计划的修改

`handoff-2026-11-24.md` §12 的 P0 是「判定判官重试是否有效」，列了三种结局。
**本文给的是它没列的第四种**：

| 原文的结局 | 是否出现 |
|---|---|
| 出现 `ok` → 修复有效，收工 | 出现了 `ok`（10 条），**但归因错误**——见 §2 |
| `attempts=2` 且 `ok` → 重试救回来的 | **未出现**（0 条） |
| 仍全是 `empty` 且 `attempts=2` → 模型不肯输出 JSON | **未出现**（0 条 `empty`） |
| **（新增）`empty` 消失、但 `attempts=2` 也为 0** | **就是这个** |

**结论改写**：

> 判官空回答**已消失**，原因是 `2026-11-24T02:36Z` 的**路由切换**，不是 1.19.0 的
> 预算/重试。1.19.0 的重试**至今零触发**，因此**不能记为已验证的修复**，但可保留为
> 未来某条路由再次空回时的兜底。**不再需要为它追加预算或改 prompt**——原文
> §12「不要再加预算」这一条，本文再加一层理由：连「预算不够」这个前提
> 都只对 32% 的样本成立。

**P0 的两项已经落地（1.20.0）**：

1. ~~修 metrics 覆盖~~ → **已修**（§5，`judge_*` 命名空间）。
2. ~~输入面独立超时预算~~ → **已给旋钮**（§6，`input.judgeTimeoutMs`，默认 0 = 不变）。

**还没决定的那半个问题**（需要操作者拍板，不是代码问题）：

- `input.judge: always` + `judgeFailClosed: true` 意味着**每一条用户消息**都可能因为
  一次模型调用超时而被拒。1.20.0 给了「把 deadline 放宽」这个杠杆，但没有改变
  「一次失败就拒整轮」这个语义。可选的下一步（都**没有**实施）：
  - 给 `input.judge` 加一档「只在结构性可疑时 fail-closed」（现在是二选一）；
  - 或者给输入判官加**连续失败熔断**（同会话连 N 次不可用后降级为记账 + 放行）；
  - 或者把 `input.judgeFailClosed` 的默认值在 `always` 档下改成 `false`（破坏性）。
- 判官自身 usage 记账：~~仍然没有~~ → **1.21.0 已做**。`JudgeChunkLike` 现在读 `usage` 与

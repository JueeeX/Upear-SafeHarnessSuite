# 事故：重试插入的空 user 消息会让整个会话永久 400（2026-11-25）

> **一句话**：宿主（DSH）的「重试本轮」会在对话历史里**追加一条 `content: []` 的 user 消息**。
> 严格校验的 OpenAI 兼容端点会拒绝**整条请求**（`empty_message_content`），
> 而这条空消息**留在历史里不走**，于是**之后每一轮都失败**——整个会话报废，只能新开。
>
> **与 SafeHarness 无关**，也不是 1.20.0 引起的。本插件的输入钩子只扫
> `source.kind === 'user'` 的消息（`src/hooks/context.ts:32-41`），既不会生成也不会删除这条消息；
> 它在账本里**一个字节的信号都没留下**——这正是要把它写下来的原因。

取证时间：2026-11-25 11:30（Asia/Shanghai）= **03:30Z**。
证据来源：会话日志 `~/.dsh/sessions/--F-AgentSecurity-Upear--/session-0540b632-…/session.v4.jsonl.zstd`
（3538 条事件）+ 账本 `~/.dsh/safeharness/audit/ledger.ndjson`。

## 2. 为什么「重试一次」会把会话毁掉

1. 重试走的是**把上一条用户输入重新投递**的路径，但这一次投递的 `content` 是**空数组**。
   日志里同一时刻的 `agent/inbox/spliced` 也是同一个形状（`content: []`, `source.kind: retry`）。
2. 空消息被 **`surfaceOp: "append"`** 写进对话历史——不是临时参数，是持久化的历史项。
3. 请求构造时它原样进入 `messages`；严格端点（本项目用的 `od` 路由）对
   **任意一条** message 做非空校验，于是一次非法 → 整个请求 400。
4. 因为它在历史里，**下一轮用户输入（哪怕完全正常）也会带着它**，所以修复不了：
   日志显示第 5 轮是一条 5 字符 + 图片的正常消息，照样 400。

| 会话 | 空的重试消息 | 首次 400 | 之后是否恢复 |

| `0540b632`（本次） | 1（seq 3524） | turn 4，`2026-11-25T03:03:18Z` | **否**（0 个成功轮次） |
| `c8a0690b` | 1（seq 3539） | turn 5，`2026-11-23T06:07:01Z` | **否**（连挂 3 轮后放弃会话） |
| `eae6c0ff` | 3（seq 342 / 408 / 2629） | turn 15，`2026-11-20T03:54:33Z` | 是（后续仍完成，当时走的是另一条路由） |

同一个缺陷从 **2026-11-19** 就能观察到（`eae6c0ff` 的 seq 342），
只是当时的路由**容忍空消息**，所以它表现为「重试有时没反应」，而不是整会话报废。
**换到严格路由之后，同一条老缺陷变成硬故障。**

## 4. 为什么账本里查不到

- 输入钩子只扫真正的用户输入（`source.kind === 'user'`），
  空的重试消息被**有意跳过**（理由见 `context.ts` 注释：tool 结果是 `role: user`，
  不能当用户输入扫）。所以它既不会被拒绝，也不会被记账。
- 失败发生在**宿主→模型**这一层（400），插件的五个面都在它外边：
  输入面已经放行（`input_checked allow`），输出面只看到「这一轮没有回答」
  （`output_reviewed warn chars=0 judge_status=skipped_empty`）。
- 结论：**这类故障在安全层里是不可观测的**。要么宿主修，要么插件加一条只读信号。

## 5. 恢复办法（操作者）

1. **这个会话救不回来**：空消息已持久化，重试一次失败一次。**新开会话**。
2. 不要在失败后连点「重试本轮」——每点一次都会再追加一条空消息。
3. 会话文件本身不要手改（`session.v4.jsonl.zstd` 是 zstd 多帧，改坏会丢历史）。

## 6. 建议的修复顺序

| 层级 | 动作 | 评价 |
|---|---|---|
| **宿主（首选）** | 重试时**不要追加空 user 消息**：复用上一条输入的引用，或直接不追加（重试只需要重新发请求） | 唯一根治点。上游问题应报给 DSH |
| 宿主（兜底） | 构造请求时跳过 `content.length === 0` 的 user 消息 | 能救回已中毒的会话 |
| **插件（只读，建议做）** | 输入钩子数一下 `payload.messages` 里的空 user 消息，写 `labels.empty_user_message=<n>` + metric。**只记账，不改消息** | 小、安全、让下一次故障一条查询就能定性 |
| 插件（**不建议**） | 在安全插件里**改写宿主历史**、把空消息删掉 | 一个安全插件静默重写对话历史，风险大于这个 bug；要做也必须先有明确决策 |

# 一、DSH 有没有插件优先级 / 顺序保证？

## 1.1 一句话结论

**没有数值优先级，也没有"安全插件优先"这种一等概念**。宿主只提供两种顺序机制：
① 同一事件名下监听器的**注册顺序**（`prepend` 只能插到队首，不是优先级数字）；
② 工具面**按 scope 分层的 guard**（单调否决，后注册者无法撤销）。
插件之间"谁先加载"由 profile patch 的条目组装顺序决定，而**组装顺序只决定注册先后，不构成语义优先级**，且更晚注册的 `prepend` 监听器会排到更前面。

佐证"没有插件优先级"：对抽取树全量 `.js` 搜 `priority`，唯一命中是插件管理器里描述"更高优先级**配置层**"（agent preset 覆盖 profile）的用户文案——
`tools/host-0.2.2/dsh/node_modules/@deepseek-ai/dsh-plugin-manager/lib/types/tools.js:54`，以及 `tools/host-0.2.2/dsh/node_modules/@deepseek-ai/dsh-plugin-manager/lib/index.js:2667` 的同一句话；
**没有任何包给插件定义数值优先级或排序 API**。
（易混淆项：`dsh-skill` 对**技能提供方**确有 `BUNDLED_SKILL_RANK = 600` 这类排名——
`tools/host-0.2.2/dsh/node_modules/@deepseek-ai/dsh-skill/lib/index.js:22-23`，「排名」只用于同名技能择优，与插件加载/监听器顺序无关；
插件自己的提示词 section `order: 190` 也只排提示词段：`plugins/dsh-safeharness/src/surface/prompt.ts:16-17`。）

## 1.2 cordis 事件派发：顺序 = 注册顺序

- `register()` 用 `options.prepend ? 'unshift' : 'push'` 往该事件名的数组里塞监听器：
  `tools/host-0.2.2/dsh/node_modules/@deepseek-ai/cordis/lib/index.js:919-928`。
  注意 `unshift` 语义：**后注册的 prepend 监听器排在更靠前**（同文件 :920），不存在"prepend 之后再按优先级排"。
- `ctx.on(name, listener, options)` 里布尔值就是 `prepend` 的简写（`{prepend: true}`）：同文件 :951-958。
- `waterfall()` 明确"最外层最先执行；某个监听器不调用 `next()` 就否决其后的全部监听器（含宿主内建行为）"，返回值是最外层监听器的返回值：
  同文件 :893-917。由此可推出两个常被忽略的事实：
  - 如果**更早**的监听器直接 `return deny` 而不 `await next()`，我们的监听器**根本不会被调用**（"first denial wins" 的另一半）；
  - 如果更早的监听器 `await next()` 后**丢弃**我们返回的 `deny` 再 `return {kind:'allow'}`，它可以把我们的拒绝改写成放行——
    `next()` 的返回值在调用方手里，cordis 没有签名/封签机制（同文件 :910-916）。
- 派发时的 scope 过滤只影响"哪些监听器可见"，不改顺序：同文件 :829-835。

## 1.3 工具管线：pre-execute（可改写）与 guard（单调）是两条不同的门

`dsh-tools` 的每次调用都是同一个三段式调度：`prepare()`（快照 + pre-execute + 审批 + guard）→ `dispatch()`（`tools/execute` 环绕 + 工具体）
→ `complete()`（`tools/post-execute` + `tools/result` 观测）：

- `prepare()`：`tools/host-0.2.2/dsh/node_modules/@deepseek-ai/dsh-tools/lib/pipeline.js:375-435`；
  `tools/pre-execute` 就在这里用 `ctx.waterfall(carrier, "tools/pre-execute", exec, () => ({kind:"allow"}))` 派发：同文件 :386。
- **审批在 pre-execute 之后、guard 之前**：`gate.kind === "ask"` → `serviceAsk()` → `approval.request({agent, toolName, callId, reason, signal})`：
  同文件 :387-391 与 :608-631；approval 事件本身只携带这几个字段：
  `tools/host-0.2.2/dsh/node_modules/@deepseek-ai/dsh-user-approval/lib/index.js:159-161`，内层默认返回 `unavailable`：同文件 :201。
- **guard 只在 pre-execute 结果为 allow 时才跑**（`decision.kind === "allow" ? this.tools.checkGuards(exec) : decision.reason`）：
  `tools/host-0.2.2/dsh/node_modules/@deepseek-ai/dsh-tools/lib/pipeline.js:402`。所以"pre-execute 被更早的监听器拒掉"时，我们的 guard 也不会被咨询。
- `checkGuards()` 先 `guards.global`、再沿 agent 的 scope 链（远祖先→近），层内按注册序，返回**第一个**非 `undefined` 的理由（"first denial wins"）：
  `tools/host-0.2.2/dsh/node_modules/@deepseek-ai/dsh-tools/lib/index.js:652-662`；`tools.guard()` 只是往当前 scope 的层 append：同文件 :645-651；
  scope 链表顺序由 `ScopedLayers.chainLayers()` 决定（远祖先在前）：
  `asar:dsh/node_modules/@deepseek-ai/dsh-scope/lib/index.js:161-168`。
- 拒绝的后果：`prepare()` 直接产出 `isError` 结果、**工具体不会 dispatch**：同 pipeline.js :404-418。
- `tools/execute` 是环绕（around）waterfall，可改 `exec`：同文件 :488-492；`tools/post-execute` 的 `block` 把结果整体换成 `isError`：
  同文件 :661-683；`tools/result` 是纯观测，监听器抛错只告警、不影响结果：同文件 :580-590。
- 批量调用里 **pre-execute 有序、只有 dispatch/工具体可并发**：
  `tools/host-0.2.2/dsh/node_modules/@deepseek-ai/dsh-tools/lib/types/batch.js:120-165`。

## 1.4 组合顺序（profile patch insert）

- 条目合成：`[...layers.map(l => l.patches), loaded.patches]` 后 `flatten`，按 `id` **首次出现者胜**：

- 插件管理器的写法注释："替换最后一个匹配的 override，或把新条目追加到既有 insert 之后"：
  `tools/host-0.2.2/dsh/node_modules/@deepseek-ai/dsh-plugin-manager/lib/types/patch.js:13-15`，查找时跳过 `insert` 行：同文件 :44-49。
- 本机 profile 里我们的条目确实在 `insert:` 块内：`C:\Users\xiaojue\.dsh\profiles\desktop\cordis.patch.yml:324-326`。

## 1.6 我们的插件应该怎么注册（以及代价）

**建议 = 双保险，缺一不可**：

1. `ctx.on('tools/pre-execute', …, { prepend: true })`：1.7.0 已落地（注册 `plugins/dsh-safeharness/src/hooks/tools.ts:63`，`prepend` 在同文件 :148）。
   它带来：看到**原始** `exec.arguments`（早于 `tools/execute` 环绕改写）、可 `deny`/`ask`、可写账本、可读会话轨迹。
   代价：顺序不是绝对第一（更早的 prepend 会抢跑，外层可改写返回值），且是异步热路径（我们的做法是"先记账再拒"，账本不可写即拒：
   同文件 :107-111、:131-139）。
2. `ctx.tools.guard(...)`：1.7.0 已落地（同文件 :153-173）。它是**唯一单调**的否决通道——正因为它独立于事件数组，
   即使某个更早的 pre-execute 监听器"吞掉"了我们的监听器（不调用 `next()` 直接 allow），只要管线走到 allow，guard 仍会执行并否决。
   代价：必须 O(1) 级、无 IO、不能 async、已过审批（用户可能被问过一次注定被拒的调用）；当前只做"名字模式 + 参数字节上限"两项
   （同文件 :159-166），抛错按拒绝处理（同文件 :168-172）。

**顺序上的最佳努力**：`prepend` 让我们排在"普通注册者"之前；若要在"多个都 prepend 的安全插件"之间再排序，宿主没有机制——
只能靠 profile 里谁先加载（`insert` 落点，UNVERIFIED）或显式协作约定，**不能承诺绝对第一**。

> **结论（问题 4）**：DSH 0.2.2 没有插件优先级数字，只有"注册顺序 + scope 分层 guard"。安全插件能做到的极限是：
> ① `prepend` 抢在普通监听器之前并保留原始参数；② `tools.guard` 作为不可撤销的单调兜底（但只在 allow 之后、且不能 ask/IO）；
> ③ 自己的账本作为独立证据链。**无法承诺"任何后装插件都不可能排在我们前面"**——后装者同样 prepend 即可抢跑，
> 且更早的监听器可以改写我们的返回值。这不是我们实现的问题，是 cordis waterfall 语义决定的。

## 2.5 覆盖在哪里停止（按可利用性排序）

1. **shell 里的二次命令**：我们只看到 `pwsh` 这一层调用与它的参数字符串；宿主不给我们子进程/文件/网络视图。
   我们对参数只做名字/标签策略与 `inspectSql`（仅 `shell`/`db`/`exec` 标签工具）：`plugins/dsh-safeharness/src/engine/tool.ts:70-155`。
   **不解析 PowerShell 语法、不做命令链分析** → `curl | iex` 这类只能靠正则规则命中。
2. **网络副作用**：宿主没有出网 seam，插件不拦截任何 fetch/socket。插件自己唯一的出网是巡检的 health 探测与通知：
   `plugins/dsh-safeharness/src/patrol/index.ts:88-89`（`fetchImpl`/`notifyImpl`）、同文件 :103-104（3s 预算）。
3. **技能正文（instructions）**：`dsh-skill` 明确把技能体当"可信本地内容"原样嵌入：
   `tools/host-0.2.2/dsh/node_modules/@deepseek-ai/dsh-skill/lib/index.js:49-53`，因此技能里"让模型忽略安全规则"这类文本
   **不被当作用户输入审**；只有它作为工具结果返回时，才落在 `results` 扫描（凭据泄露/注入标记）范围内。
   这是当前最大的语义盲区（技能=用户自己安装的代码，威胁模型上可接受，但必须在文档里说清）。
4. **模型的推理内容（reasoning）**：流里确实有 `reasoning-delta`：`tools/host-0.2.2/dsh/node_modules/@deepseek-ai/dsh-llm/lib/types/assistant-stream.js:44-49`，
   但输出扫描只累计 `text-delta`（`plugins/dsh-safeharness/src/hooks/llm.ts:131-140`）→ **思考内容既不审也不缓冲**。
5. **工具体内部**：`pre-execute`/`guard` 都在 dispatch 之前，`post-execute` 只能看到结果
   （`tools/host-0.2.2/dsh/node_modules/@deepseek-ai/dsh-tools/lib/pipeline.js:402` vs 同文件 :492 vs 同文件 :672）；
   一旦工具体开始执行，我们无法撤回。
6. **审批通道的信息量**：`approval/request` 只有 `toolName`/`callId`/`reason`：
   `tools/host-0.2.2/dsh/node_modules/@deepseek-ai/dsh-user-approval/lib/index.js:159-161`，所以审批桥只能做"名字级"策略、不能审参数
   （`plugins/dsh-safeharness/src/hooks/approval.ts:1-13`）。
7. **MCP server 侧**：工具描述、资源、server 内部行为都在宿主之外；我们只能审"调用"与"返回结果"。
8. **子代理的模型路由/预算**：子 agent 的输出是否也过 `llm/stream` 取决于它用的 llm 服务实例；同一 profile 下应为同一服务，
   但逐包确认 **UNVERIFIED**（`dsh-subagent` 未抽取）。
9. **面板与命令**：只读/受门控，不构成防护面；但它们把"我们看到了什么"暴露给操作者，本身受零内容约束
   （`plugins/dsh-safeharness/src/panel/settings.ts:1-13`、`plugins/dsh-safeharness/src/audit/ledger.ts:2-3`）。
10. **审计内容**：账本只存 hash 与长度（`plugins/dsh-safeharness/src/audit/ledger.ts:2-3`、同文件 :206-227），事后无法还原原文——这是设计选择，不是缺陷。

> **结论（问题 2 前半）**：能力面是"输入 / 工具调用（含单调兜底）/ 工具结果 / 模型输出 / 审批 / 预算 / 审计 / 姿态 / 巡检"九块，
> 五套工具来源（内置、MCP、技能、子代理、工作流/PTC）**都能在调用级被拦截**，因为它们共用同一条 `prepare()` 管线。
> 覆盖的终点是"工具体开始执行之后"和"宿主之外"：shell 内部、网络、技能正文、模型推理、MCP server 自身。

# 给用户的回答要点

- **没有插件优先级。** DSH 0.2.2 不存在"插件 priority"机制；顺序只由"同一事件名下监听器的注册顺序"决定，`prepend` 只是插到队首
  （`tools/host-0.2.2/dsh/node_modules/@deepseek-ai/cordis/lib/index.js:919-928`），而且后装的插件照样能 prepend 排到我们前面。
- **我们做到的是最佳努力 + 单调兜底。** 1.7.0 里四个监听器全部 `{ prepend: true }`
